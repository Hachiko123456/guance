# GPU-first inference and CPU fallback (2026-10-20)

This document describes the MARVEL V2 inference device policy, its runtime
contracts, the isolated CUDA environment, and how to switch between `auto`,
`cpu` and `cuda`. It does not change FableDan, training, capture, proxy,
certificate, or game-action behavior.

Current delivery split:

- **Source + isolated CUDA environment**: GPU-first `auto` was independently
  verified (real `cuda:0` execution, not just `is_available()`), and the accepted
  CPU-only environment returns to CPU with an explicit reason.
- **Old fresh no-capture frozen package (2026-10-20 previous round)**: contains
  no Torch/MARVEL runtime or checkpoint. MARVEL is unavailable/fail-closed; it
  is **not** a frozen GPU distribution.
- **Final local MARVEL GPU onedir (2026-10-20 delivery)**: built by
  `build_release.py --profile marvel-gpu` from the final local commit. It vendors
  the already-accepted `torch 2.13.0+cu126` + CUDA DLLs, the frozen MARVEL
  source/native tree, the real iter2000 checkpoint and the descriptor under
  `_internal/marvel_runtime`. The worker resolves those package assets itself;
  it does not read the repository, the Guandan worktree, a development venv or
  `PYTHONPATH`. Default `auto` uses `cuda:0` on this machine, falls back to CPU
  only for genuine unavailability, and forced `cuda` fails closed without a CPU
  or model fallback. This is local evaluation only; cross-machine behavior is
  **UNVERIFIED** and redistribution is **NOT_AUTHORIZED**.
- Phase 7 is **PAUSED / NOT STARTED / NOT AUTHORIZED**.

The authoritative capability matrix is
[PROJECT_STATUS.md](PROJECT_STATUS.md).

## 1. Policy

The only decision point is `src/guance/infrastructure/model/device_policy.py`.
There are no per-layer GPU checks.

| requested | contract | Torch/environment | result |
| --- | --- | --- | --- |
| `auto` | `marvel_v2.device.v1` | CUDA build, device visible, real probe OK | `cuda:0`, `CUDA_PROBE_OK`, fallback=false |
| `auto` | `marvel_v2.device.v1` | CPU-only Torch | `cpu`, `CPU_ONLY_TORCH`, fallback=true |
| `auto` | `marvel_v2.device.v1` | CUDA build, no visible device | `cpu`, `NO_CUDA_DEVICE`, fallback=true |
| `auto` | `marvel_v2.device.v1` | CUDA build, device present but unavailable | `cpu`, `CUDA_NOT_AVAILABLE`, fallback=true |
| `auto` | `marvel_v2.device.v1` | probe fails for a clearly classified initialization/driver/kernel reason | `cpu`, `CUDA_INIT_UNAVAILABLE`, fallback=true |
| `auto` | `marvel_v2.device.v1` | probe OOM / assert / unknown execution error | **fail closed** `MODEL_INFERENCE_FAILED`, no CPU retry |
| `cpu` | `marvel_v2.device.v1` | any | `cpu`, `FORCED_CPU`; CUDA is not probed |
| `cuda` | `marvel_v2.device.v1` | CUDA unavailable (any classified reason) | **fail closed** `MODEL_UNAVAILABLE`, no CPU fallback |
| `auto`/`cpu` | `marvel_v2.cpu.v1` (legacy) | any | `cpu`, `LEGACY_CPU_CONTRACT` |
| `cuda` | `marvel_v2.cpu.v1` (legacy) | any | **fail closed** `MODEL_UNAVAILABLE` |

The probe allocates tensors on `cuda:0`, performs a matmul, calls
`torch.cuda.synchronize`, and checks the numeric result. `torch.cuda.is_available()`
or the GPU model name alone is never accepted as evidence.

`torch.version.cuda` is reported separately as `torch_cuda_build`; it is not the
execution device. A CUDA build running on CPU reports `actual_device=cpu` and
`torch_cuda_build=12.6`, never a fabricated CPU-only build.

After a model has loaded or a recommendation has started, OOM, device assert,
non-finite output, timeout, identity mismatch, tampered weights or invalid input
all fail closed. There is no CPU retry and no FableDan/model fallback.

## 2. Runtime contracts

- `marvel_v2.cpu.v1` — the original Phase 2-5 CPU-only meaning. It stays valid
  and is never silently upgraded; it forces CPU and rejects `cuda`.
- `marvel_v2.device.v1` — new device-flexible contract. The bundle still pins
  the exact checkpoint SHA-256, iteration, source fingerprint, native identity,
  Torch version and CUDA build in its deployment descriptor. Only the execution
  device changes; model identity and weights do not.

The task-local device bundles are generated by
`scripts/build_gpu_first_bundles.py` under
`build/acceptance/guance-gpu-first-inference-20261020/bundles` (for the cu126
interpreter) and `.../bundles-cpu-env` (descriptors pinned for the accepted
CPU-only Torch interpreter). Both sets are descriptors for the same
`marvel_v2.device.v1` contract; `bundles-cpu-env` is not a CPU-only Torch build.
They contain small JSON descriptors only; checkpoints are read in place and are
never copied or modified.

## 4. Selecting a device

Precedence: `GUANCE_MODEL_DEVICE` environment variable, then the persisted
`model_device` preference (`auto` default), then `auto`.

- Default `auto` (GPU when available, otherwise CPU with a visible reason):

```powershell
$env:GUANCE_MODEL_DEVICE = 'auto'
$env:PYTHONPATH = 'D:\project\guance\src'
$env:GUANCE_MARVEL_V2_SOURCE = 'D:\project\guance\build\acceptance\guance-model-platform-20261016\phase2\runtime\marvel-e5c82e7c-d7acbc8d\source'
$env:GUANCE_MARVEL_V2_CHECKPOINT = 'D:\project\guandan\runs\comparison_delivery\dataset\m09_candidate_iter002000.pt'
D:\project\guance\build\gpu-env-20261020\Scripts\python.exe -m guance
```

- Forced CPU (same environment, still reports `torch_cuda_build=12.6`):

```powershell
$env:GUANCE_MODEL_DEVICE = 'cpu'
```

- Forced CUDA (fails explicitly if CUDA is unavailable):

```powershell
$env:GUANCE_MODEL_DEVICE = 'cuda'
```

The worker inherits the interpreter of the running application, so launch the
application itself with the GPU environment to use GPU inference. The worker
command line also accepts `--device auto|cpu|cuda` internally; bundles can
never choose an interpreter or executable.

The accepted CPU environment remains usable with `py -3.12 -m guance`; `auto`
then reports `CPU_ONLY_TORCH` and uses CPU. This is an environment limitation,
not a claim that the machine has no GPU.

## 5. Observability

Loaded/unavailable metadata exposes bounded fields through the existing status
channel and the settings model card:

- `requested_device` (`auto`/`cpu`/`cuda`)
- `actual_device` (`cpu`/`cuda:N`)
- `device_fallback` (boolean; separate from model fallback counters)
- `device_reason` (stable code such as `CUDA_PROBE_OK`, `CPU_ONLY_TORCH`,
  `FORCED_CPU`, `LEGACY_CPU_CONTRACT`, `CUDA_INIT_UNAVAILABLE`,
  `CUDA_PROBE_OOM`)
- `torch_cuda_build` (build information, not the execution device)
- `device_evidence` (bounded parameter/buffer/cache device evidence)
- `runtime_contract`, `model_version`, checkpoint SHA-256

The UI shows “当前使用 GPU 推理（cuda:0）” or
“GPU 不可用，当前使用 CPU 推理：原因……” and never counts a device fallback as
a model fallback.

## 6. Acceptance runner

```powershell
# full fixed input on one device
build\gpu-env-20261020\Scripts\python.exe -B scripts\run_gpu_first_inference_acceptance.py fixed `
  --bundle-dir build\acceptance\guance-gpu-first-inference-20261020\bundles\marvel-v2-iter002000-device `
  --device cuda --output build\acceptance\guance-gpu-first-inference-20261020\fixed-input-gpu.json

# iter100/iter500/iter2000 load + one legal recommendation
... smoke --bundle-dir ...\bundles\marvel-v2-iter002000-device --device cuda --output ...\model-smoke-gpu.json

# three independent cold starts per device
... coldstart --bundle-dir ... --device cuda --runs 3 --output ...\cold-start-gpu.json

# CPU/GPU probability/mask/action comparison
... numeric --bundle-dir ... --device cpu --output ...\numeric-cpu.json
... numeric --bundle-dir ... --device cuda --output ...\numeric-gpu.json
... compare --cpu ...\fixed-input-cpu.json --gpu ...\fixed-input-gpu.json `
  --numeric-cpu ...\numeric-cpu.json --numeric-gpu ...\numeric-gpu.json --output ...\numeric-parity.json

# real CPU-only-Torch worker: auto->CPU, cuda->explicit failure
py -3.12 -B scripts\run_gpu_first_inference_acceptance.py no-gpu `
  --bundle-dir build\acceptance\guance-gpu-first-inference-20261020\bundles-cpu-env\marvel-v2-iter002000-device `
  --output build\acceptance\guance-gpu-first-inference-20261020\no-gpu-worker.json
```

Repair-1 notes:

- The `compare` gate validates non-empty records, exact declared coverage,
  unique/corresponding decision identities, equal vector lengths, finite values,
  exact mask/argmax agreement and the pre-declared elementwise rule
  `abs(cpu-gpu) <= atol + rtol * max(abs(cpu), abs(gpu))`. It reports the 32
  action/path-score records and the 4 probability/mask records separately.
- `recompute-perf` reads existing performance samples and recomputes median/max
  of round means. It marks per-request P95 `UNVERIFIED` because only round
  means were recorded; it does not rerun the benchmark.
- `fixed-input-cpu.json` / `numeric-cpu.json` / `cold-start-cpu.json` were
  produced by the cu126 build forced to CPU. Real CPU-only Torch evidence is
  `no-gpu-worker.json`, `fixed-input-cpu-only-repair1.json` and
  `numeric-cpu-only-repair1.json` under the Repair-1 evidence root.

## 7. Rollback / returning to the CPU environment

1. Unset `GUANCE_MODEL_DEVICE` (or set `auto`).
2. Launch the application with the original interpreter:
   `py -3.12 -m guance` (or the existing packaged executable).
3. The legacy `marvel_v2.cpu.v1` bundles keep their original CPU-only
   semantics; the accepted CPU environment and all user data remain unchanged.
4. The isolated environment lives only under `build/gpu-env-20261020` and can
   be deleted later without touching checkpoints, captures, preferences or the
   accepted CPU Python installation.

No checkpoint, capture, frozen runtime source, or Phase 1-5 evidence is
modified by switching devices.
