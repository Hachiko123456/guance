# Guance 功能验收标准（大模型执行版）

版本：0.2.1
维护日期：2026-10-01
适用范围：每次新增、修改、重构或打包发布前。
权威性：本文件是验收顺序和放行规则的总入口；`docs/UI_ACCEPTANCE.md`、`docs/DIAGNOSTICS.md` 和 `docs/USER_GUIDE.md` 是补充材料。

## 1. 给验收大模型的执行规则

你是 Guance 的验收执行器，不是功能实现器。每次执行必须：

1. 先读取本文件、`AGENTS.md`、本次变更的 diff 和相关测试；
2. 判断变更影响的验收 ID；
3. **按 P0 → P1 → P2 顺序执行**，不得只挑容易通过的项目；
4. P0 任一失败立即判定“不可交付”，停止宣称验收通过；
5. 自动化测试通过不能替代 Windows 实机验收；实机未做时必须标记“未验证”，不能写成“通过”；
6. 不得为了验收而自动点击大掼蛋、自动出牌、重放网络请求、修改或导出用户隐私数据；
7. 不得安装证书、修改系统代理、启动真实采集器，除非本次验收明确得到用户授权，并且每一步都有恢复和清理检查；
8. 所有失败都要记录：验收 ID、复现命令/动作、实际结果、预期结果、日志或截图路径、建议修复位置；
9. 最终输出必须包含通过、失败、跳过、未验证四类清单，以及是否允许交付。

### 1.1 结果状态

- **通过**：有可复现的自动化结果或实机证据，且满足预期。
- **失败**：结果不满足预期，或出现安全/数据/代理残留风险。
- **跳过**：因测试前置条件不满足而未执行，必须说明原因；不能计入通过率。
- **未验证**：设计了验收步骤但当前环境无法执行，例如没有 Windows 实机或没有用户授权。

### 1.2 责任分工与自动编排

每个新增、修改、重构或发布需求都必须生成与本次变更对应的验收映射。主代理负责最终维护本文件、`docs/ACCEPTANCE.md` 和本次任务的验收记录，并负责最终放行裁定。

- `analyst`：需求含糊时提炼需求、边界、影响范围和验收条件；只读。
- `architect`：涉及跨模块接口、数据结构、依赖或关键技术选择时，提供最小设计和设计验收条件；只读。
- `implementer`：在明确写入授权范围内实现功能，并提供实现相关测试证据。
- `test_engineer`：独立设计和执行测试，生成“需求—验收 ID—测试/证据—结果状态”矩阵；不得代替主代理修改最终验收文档或作出放行决定。
- `reviewer`：独立检查实际差异、验收覆盖、安全边界和测试遗漏；只读。

架构评审默认由主代理决策并记录采用的方案，不设置强制用户确认门槛。需求明确且可复用现有架构时，也不必调用 `architect`；只有重大需求歧义、不可逆操作、外部副作用或明确需要用户选择时，才暂停并请求用户决定。

验收输出必须包含：通过、失败、跳过、未验证四类清单；受影响的验收 ID；实际命令或动作；工作目录；退出码或观察结果；证据位置；剩余风险；以及是否允许交付。没有执行的检查不得记为通过。

### 1.3 先写标准，再实现，再依据证据验收

1. **实现前，主代理写标准。** 从原始需求提取可观察结果、边界、异常和回归要求；选取受影响的 P0/P1/P2 ID，未被覆盖的新行为使用任务内稳定 ID。标准不得事后照着实现结果倒推。
2. **复用现有记录。** 优先补充已有任务验收文件；小任务可直接使用本地内部状态记录的验收章节（内部记录不属于公开交付）。主代理在状态记录中注明验收记录路径或章节，并在每次委派任务书中引用。同一任务重复执行不得追加重复章节或建立第二套标准；通用规则变化才更新本总标准，入口变化才更新 `docs/ACCEPTANCE.md`。
3. **交给子代理执行。** `implementer` 按标准实现并提交单测证据；按风险需要调用 `test_engineer` 独立补测、`reviewer` 审查覆盖和风险。不要求所有小任务机械经过五种角色。子代理发现标准缺项时向主代理报告和建议，不自行降低标准或改写最终记录。
4. **按单写入者规则交接。** 主代理写标准/记录时不得与子代理写代码、写测试或执行会改变文件/缓存/环境的检查并行。标准完成后再授予实现写入权；最终验收前收回影响候选状态的写入权。
5. **主代理最终复验并记录。** 主代理核对实际差异（含新增和未跟踪文件），在最终候选状态运行关键验证；只依据实际证据裁定。后续相关修改必须重跑受影响检查；未执行或环境受限不等于通过。
6. **不为通过而改标准。** 需求或已确认事实发生变化时，主代理记录标准变更理由和影响并重新验证；不得删除失败项、削弱断言或把未验证改写为通过。

任务验收映射至少包含下表字段（模板行不是已执行结果）：

| 任务验收 ID / 关联总标准 ID | 原始需求 | 前置条件与输入/动作 | 可观察的预期结果 | 验证方法与证据要求 | 优先级/阻断条件 | 执行状态 |
|---|---|---|---|---|---|---|
| `<任务ID>-AC-001` / `<受影响ID>` | `<需求原文或可追溯摘要>` | `<正常/边界/异常场景>` | `<明确的通过判据>` | `<已核实的命令或人工步骤；结果证据位置>` | `<P0/P1/P2及阻断条件>` | 待执行 |

“待执行”用于尚未开始的计划项，不是第五种验收结论。最终记录必须将其归入通过、失败、跳过或未验证，写明真实命令/动作、工作目录、退出码或观察结果、证据和剩余风险；第 6 节的放行标准保持不变。

## 2. 重要程度与阻断规则

### P0：安全、授权、数据完整性、核心可用性（任一失败即阻断）

| ID | 验收目标 | 必须证明 |
|---|---|---|
| P0-001 | 应用可启动且可退出 | Python 3.12 x64 可导入；主窗口能启动；退出后无 Guance/mitmdump 子进程 |
| P0-002 | 明确授权边界 | 未勾选授权不能执行；取消授权不写证书、不改代理；`consent=False` 是硬 no-op |
| P0-003 | 证书路径和信任检查一致 | mitmproxy 生成证书的目录与运行时检查目录相同；已授权证书不会被误报为 missing/untrusted |
| P0-004 | 证书操作范围正确 | 只操作当前 Windows 用户 Root 存储；不写 LocalMachine；失败不绕过组织策略 |
| P0-005 | 代理安全 | helper 未 ready 前不修改系统代理；启动失败能恢复；停止、异常退出、代理冲突都有恢复路径 |
| P0-006 | 隐私边界 | 日志、诊断包和 UI 不包含 Cookie、Authorization、私钥、原始 payload、对手隐藏手牌或模型权重 |
| P0-007 | 不自动执行游戏 | 代码和实机流程只提供建议；不自动点击、出牌、请求重放或修改流量 |
| P0-008 | 状态可信 | 漏包、重复包、未知命令、非法牌码、非法状态版本会暂停推荐，不猜测、不继续污染状态 |
| P0-009 | 必需模型不可静默回退 | 模型缺失、损坏、不兼容、超时或崩溃时明确报错；生产模式不切换到规则假推荐 |
| P0-010 | 修复回归 | 对每个已修复 bug 都有一个最小回归测试，能在修复前失败、修复后通过 |

### P1：核心功能正确性（P0 全通过后执行）

| ID | 验收目标 | 必须证明 |
|---|---|---|
| P1-001 | 协议解析 | 实时样本解析出级牌、本人座位、首出座位；历史样本动作数回归一致 |
| P1-002 | 状态重建 | 确认动作递增状态版本；迟到推荐被丢弃；局面错误暂停推荐 |
| P1-003 | 采集模式 | 无上游代理可构建 direct；HTTP/mixed 上游可构建 upstream；凭据不进入命令或日志 |
| P1-004 | helper 生命周期 | 启动、ready、异常退出、停止顺序正确；reader 线程和子进程最终清理 |
| P1-005 | 模型推理 | 真实 `best.npz` 可加载；可用快照产生合法推荐；latest-only 队列和 CPU 线程限制有效 |
| P1-006 | 推荐边界 | 推荐只来自当前公开局面和本人手牌；不是本人回合不显示建议；状态变化后清除旧建议 |
| P1-007 | 诊断 | 状态、错误码、恢复建议可见；诊断导出成功且脱敏；日志有界并轮转 |
| P1-008 | UI 操作闭环 | 开始、授权、停止、修复网络、移除授权、导入模型、导出诊断、浮窗和三页导航都有信号消费者和可观察状态变化 |
| P1-009 | 启动顺序 | 助手准备完成后提示重新打开大掼蛋；未捕获游戏帧时不能伪造“对局已同步” |
| P1-010 | 配置兼容 | 旧数据目录、已有证书、已有上游代理和无代理环境不会导致静默错误或残留设置 |

### P2：体验、兼容性、发布质量（P0/P1 全通过后执行）

| ID | 验收目标 | 必须证明 |
|---|---|---|
| P2-001 | Windows UI | Windows 10/11 主窗口、授权弹窗、设置、诊断页可用 |
| P2-002 | 缩放与主题 | 100%、125%、150%、200% 下核心按钮和建议不截断；浅色、深色、系统主题可用 |
| P2-003 | 中文提示 | 首屏错误告诉用户下一步；不把 Python 堆栈或内部 PID/端口作为主要用户提示 |
| P2-004 | 打包 | PyInstaller onedir 构建成功；发布包含 QML、mitmdump、addon 和模型；无需安装 Python/NumPy/mitmproxy |
| P2-005 | 文档 | README、用户指南、架构、诊断、安全和许可证文档与实际行为一致 |
| P2-006 | 仓库卫生 | 不提交 `.mitm`、Cookie、私钥、个人日志、训练权重和本机证书材料 |

## 3. 标准执行流程

构建入口版本说明：本次文档更新单独纳入 `Guance.spec`，未提交本地修改过的构建脚本。涉及此规格时使用 `python -m PyInstaller --noconfirm --distpath release --workpath build/pyinstaller Guance.spec`，准备和检查步骤见 `docs/BUILD.md`。下列旧构建脚本命令仅在确认该脚本已迁移到维护规格、不会覆盖规格文件后使用；这不是免除完整打包和实机验收。

### 阶段 A：变更识别

记录：

- 变更摘要和 Git diff；
- 影响路径；
- 影响验收 ID；
- 是否涉及 Windows、证书、代理、真实模型、打包或用户数据；
- 是否需要用户授权的实机步骤。

路径到验收层的默认映射：

| 变更路径 | 至少执行 |
|---|---|
| `src/guance/domain/**` | P0-008、P1-001、P1-002、相关 domain tests |
| `src/guance/infrastructure/protocol/**` | P0-008、P1-001、P1-002、protocol tests |
| `src/guance/infrastructure/capture/**` | P0-005、P0-006、P1-003、P1-004、runtime tests |
| `src/guance/infrastructure/windows/**` | P0-002～P0-005、P1-003、P1-004；Windows 实机项 |
| `src/guance/application/runtime/**` | P0-003～P0-005、P1-003、P1-004、integration tests |
| `src/guance/presentation/**` | P0-002、P0-006、P0-007、P1-007、P1-008、P2-001～P2-003 |
| `src/guance/infrastructure/model/**` | P0-009、P1-005、P1-006、model tests |
| `scripts/**`、`Guance.spec`、`pyproject.toml` | P0-001、P2-004、完整打包 smoke |
| `docs/**` | P2-005，并检查文档是否与实现一致 |

### 阶段 B：快速阻断检查（每次必跑）

在仓库根目录执行：

```powershell
py -3.12 -c "import sys, struct; assert sys.version_info[:2] == (3, 12); assert struct.calcsize('P') * 8 == 64"
py -3.12 -m compileall -q src
py -3.12 -m pytest tests/runtime tests/integration tests/acceptance -q
```

若本次修改了 GUI，再执行：

```powershell
py -3.12 -m pytest tests/presentation tests/ui_acceptance -q
```

若本次修改了领域、协议或模型，再执行对应目录测试。

### 阶段 C：完整自动化回归

只要 P0 或核心代码有变化，必须执行：

```powershell
py -3.12 -m pytest -q
```

所有失败都要追到具体测试；不得以“已有失败”覆盖新失败。若环境缺少可选私有模型，允许按测试中的明确 skip 记录，但不能把 skip 当通过。

### 阶段 D：打包与启动 smoke

修改发布、依赖、QML、运行时资源或入口后执行：

```powershell
py -3.12 scripts/build_release.py --clean
& .\release\Guance\Guance.exe --exit-after 3
```

检查：

- 进程退出码为 0；
- 窗口资源、QML、模型、`runtime/mitmproxy/mitmdump.exe`、`runtime/mitmproxy/addon.py` 都存在；
- 不出现 Qt/QML 导入错误；
- 不遗留 Guance、mitmdump 或代理接管。

### 阶段 E：Windows 实机验收（需要明确用户授权）

自动化通过后，才允许在用户授权的 Windows 10/11 电脑执行：

1. 记录开始前的当前用户代理、自动配置、绕过列表和相关进程；
2. 首次启动 Guance，确认出现**应用内授权说明**；未勾选、取消和关闭弹窗都不得改证书或代理；
3. 勾选并同意，确认仅当前用户证书存储发生预期变化；
4. 确认 helper ready 后才接管代理；失败时代理保持原值；
5. 重新打开大掼蛋，进入支持的经典玩法；只由用户进行游戏操作；
6. 只验证本人手牌与公开信息同步，验证建议可见且不自动出牌；
7. 点击停止，确认先恢复原代理，再退出 helper；
8. 强制关闭/重启一次，确认无残留代理和子进程；
9. 导出诊断包，检查脱敏内容；
10. 若系统已有其他代理软件，重复检查上游模式和恢复结果。

以下情况不得在没有用户明确授权时执行：证书安装/删除、系统代理切换、真实游戏流量捕获、网络安全软件放行、删除用户配置。

## 4. 回归缺陷的最低验收要求

每个 bug 修复必须同时提交：

1. 根因说明；
2. 修复文件；
3. 一个能复现根因的回归测试；
4. 直接相关测试命令及结果；
5. 受影响层的完整测试结果；
6. 若涉及 Windows 真实能力，自动化测试之外的实机步骤和未验证项；
7. 是否需要重新打包；
8. 用户可见行为变化和恢复方式。

本次证书/网络组件类 bug 的最低回归项为：

- 证书生成目录与证书检查目录一致；
- 已存在且已信任证书不会误报 missing/untrusted；
- `consent=False` 不调用安装/删除器；
- 安装失败显示明确错误且不启动采集；
- helper 未 ready 不改代理；
- 启动失败恢复原代理并清理 helper；
- 停止和异常退出无代理/进程残留；
- 首次授权弹窗真实可见、可取消、未勾选不能继续。

## 6. 最终放行标准

只有在以下条件全部满足时，才能对用户说“验收通过”：

- 所有受影响的 P0 项通过；
- 所有受影响的 P1 项通过；
- P2 中与本次变更相关的项目通过；
- 完整自动化回归没有新增失败；
- 需要 Windows 实机的项目已通过，或明确标记为未验证并声明“不可作为生产验收通过”；
- 没有残留代理、采集子进程、未授权证书操作或敏感数据泄露。
